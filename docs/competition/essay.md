# 让 Agent 的工作看得见

仓库：https://github.com/jinyaxuan/TeamPulse

我们做 TeamPulse，是因为团队里的编码 Agent 越来越多，而它们的工作默认是看不见的。一个 Agent 在改接口，另一个 Agent 在补测试，人在聊天窗口里发需求。三边各自以为自己掌握了进度，直到两个分支改到同一批文件，或者一项需求做完了却说不清验收标准是什么。

看板解决不了这件事。看板上的卡片是人搬上去的，Agent 不会自己把终端里的进度搬过去。聊天记录也解决不了，它能保存结论，但不能约束阶段，更不能在两个 Agent 同时碰同一个文件时提醒任何一方。

TeamPulse 选择记录 Agent 已经发生的动作。设备用认领码绑定到人，之后这台机器上的任务、心跳和文件触碰都归到这个账号。面板据此显示谁正在做什么、在哪个分支、碰过哪些文件，并标出重叠。冲突不再等到合并时才出现。

只看见还不够。需求如果继续停在对话里，看见的只是碎片。我们给工作项加了一条不能跳步的生命周期：录入、澄清、就绪、指派、进行、待验收、通过。也可以打回或取消。验收策略允许人工、Agent，或两者都要通过；执行者不能给自己验收，通过时要逐条确认验收标准。这样一项工作结束时，留下的是阶段、证据和评审，不是一段无法复查的对话。

判断优先级和“能不能开工”仍然容易凭感觉。我们接了一个外部模型 JEV，让它只回答四件事：建议优先级、要不要先澄清、适不适合交给 Agent、按当前描述交付的风险有多高。项目默认关闭，打开后才会把工作项内容发到外部服务。JEV 不能改状态，不能指派，也不能替人验收。负责人每次只能采纳一条当前版本上的建议：调整优先级，或把刚录入的事项转入澄清。采纳动作单独记账。

这个边界是故意留的。模型可以给一个分数，但不该在没人看过的情况下改掉团队的优先级。分数没有理由说明时，更不该自动触发下一步。所以 TeamPulse 里，Agent 负责执行和上报，人负责采纳和验收，系统负责把两边都留下。

从 2026 年 4 月 25 日的第一次提交到 9 月 26 日的工作项与 JEV，仓库里保留了 118 个提交，包括部署失败后的重试。我们没有把这些过程整理成一条顺利的故事。TeamPulse 要记录的，本来就是工作实际发生的顺序。
